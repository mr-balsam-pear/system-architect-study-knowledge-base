# 系统架构设计师论文 · 可套用模板

> 来源：从 `docs/论文/练习/` 的 4 篇练习（云原生 v0.1/v0.2、AI 辅助研发、高可用与韧性）反向提炼。
> 用法：**换题不换骨架，换段落不换项目**。考场上 10 分钟完成选题 + 写提纲，其余时间填字。
>
> **考试形式：机考（键盘输入，系统实时显示字数）**，不是纸考手写。
> 硬指标：**论文总字数 ≥ 2500**（摘要 300～400 + 正文 2000～3000，实操取摘要 340 + 正文 2500 ≈ 2840）。
> ⚠️ 字数低于 2500 **直接降档到 30 分以下**，这是最致命的红线。

## 一、考前 15 分钟与考场流程

### 时间总盘（下午场连考）

```
14:30 — 18:00  案例分析 + 论文 连考，共 210 分钟
  ├─ 案例分析：控制 75～90 分钟完成并交卷
  ├─ 交卷后立即进入论文，不能返回案例
  └─ 论文实际可用：120～135 分钟（案例省下的时间归论文）

⚠️ 不要在案例上无计划地拖时间，也不要过早交卷浪费案例时间。
```

### 论文段流程（以 120 分钟计）

```
拿到 4 道题
  │
  ├─ 0～10 min：读 4 题 + 选题。翻到本文第 6 节《论题 → 模块选择表》定分论点
  │
  ├─ 10～15 min：在草稿纸列提纲 —— 6 个小标题 + 每个标题下 3 个要点
  │
  ├─ 15～25 min：写摘要（340 字）
  │
  ├─ 25～110 min：写正文六段（约 2500 字）
  │
  └─ 110～120 min：查字数、错别字、数据前后一致性
```

**关于摘要先写还是后写**：两种打法都可行，但要选定一种练熟。

- **先写摘要**（推荐给本模板使用者）：摘要定型后正文有稳定框架，不易跑偏。
- **后写摘要**：正文写完后压缩成摘要，内容必然一致。

无论哪种，**摘要的四个维度必须与正文四个分论点一一对应**。

## 三、摘要模板（目标 340 字）

### 四句结构

```
【第1句 60字】时间 + 角色 + 项目 + 投资周期 + 建设内容
【第2句 80字】业务压力 + 传统架构暴露的问题（对应论题）
【第3句 130字】采用什么架构 + 核心技术栈 + 围绕哪几个原则/维度 + 具体做了什么
【第4句 70字】上线时间 + 量化成果 + 一句结论
```

### ⚠️ 摘要硬约束

- **目标 340 字**（官方规定 300～400 字）。机考有实时字数统计，直接看数字。
- 你现有练习里有两篇写到 455～462 字，**超出官方 400 字上限**，要压回 340～360。
- 第 3 句最容易写长。**四个维度各用一句话，每句不超过 35 字**。

## 四、正文六段式骨架

> 全文用「一、二、三」编号，正文中直接写小标题。

```
一、项目背景与本人职责          ← 固定，约 300 字
二、【分论点 1】                ← 论题相关，约 500 字
三、【分论点 2】                ← 论题相关，约 500 字
四、【分论点 3】                ← 论题相关，约 500 字
五、【保障类分论点】            ← 治理/监控/安全/容灾，约 400 字
六、项目成效与总结              ← 固定，约 300 字
                          正文合计约 2500 字
```

### 每个分论点章节的统一写法（四步，务必按顺序）

```
① 痛点（80字）：传统做法下有什么问题 + 造成什么后果
② 措施（150字）：我们决定怎么做，为什么这么选（体现架构决策）
③ 细节（250字）：具体技术方案 + 产品名 + 关键参数 + 一个真实场景举例
④ 效果（70字）：量化对比 —— "由 X 降低到 Y" / "从 X 提升至 Y"
```

**③ 是拿分点，必须有具体技术名词和数字**；④ 是区分点，必须有前后对比。

## 五、段落模块库（核心资产 · 按论题挑 3～4 段直接拼）

> 这是 4 篇练习里已经写好、可以直接搬的段落。每段都已带痛点、措施、细节、效果四要素。

### 模块 A · 自动化（CI/CD 流水线）

**适用**：云原生、DevOps、软件过程改进、研发效能

```
在传统部署模式下，应用发布通常需要人工完成代码打包、服务器部署、配置修改以及服务重启等工作，
不仅效率低，而且容易因人为操作失误导致系统故障。为此，我们基于 Kubernetes 与 DevOps 理念
构建了自动化持续交付平台。开发人员将代码提交至 GitLab 仓库后，系统自动触发 Jenkins 流水线，
依次完成 Maven 编译与单元测试、SonarQube 静态代码质量扫描、Docker 镜像构建、镜像推送至
Harbor 私有仓库、Kubernetes 自动部署与灰度发布。同时，我们在流水线中集成自动化测试机制，
包括接口测试、回归测试以及安全漏洞扫描；发布完成后自动执行健康检查与回滚策略。

通过自动化流水线建设，项目平均发布时间由原来的2小时缩短至15分钟，人工部署错误率显著下降。
```

### 模块 B · 服务化（微服务拆分 + 服务治理）

**适用**：微服务、架构风格、领域驱动设计、服务治理

```
项目初期采用传统单体架构，多个业务模块部署在同一个应用中，导致系统之间耦合严重，
一旦某个模块出现问题，容易影响整体系统稳定性。为解决上述问题，我们基于微服务架构思想，
结合领域驱动设计（DDD）理念，按照业务边界将系统拆分为会员中心、订单中心、支付中心、
营销中心、库存中心等多个独立微服务，并通过 Spring Cloud 与 Nacos 实现服务注册与配置管理。
内部服务采用 OpenFeign 实现远程调用，使用 Gateway 统一网关实现路由转发与权限控制，
使用 Sentinel 实现服务限流与熔断，使用 Redis 与消息队列实现缓存与异步解耦。
此外，我们将短信服务、认证服务、主数据服务等公共能力沉淀为统一基础服务，实现能力复用。

通过服务化改造，系统实现了"高内聚、低耦合"的架构目标，各业务团队可以独立开发、
测试与部署对应服务，大幅提升了研发效率与系统扩展能力。
```

### 模块 C · 弹性（三层弹性 + 流量削峰）

**适用**：高并发、性能设计、弹性架构、秒杀类场景

```
航空业务具有明显的流量波峰波谷特征，例如节假日促销、会员活动期间，系统访问量会出现大幅增长。
针对这一问题，我们从实例层、网络层与数据层三个维度构建系统弹性能力。
实例层基于 Kubernetes 的 HPA（Horizontal Pod Autoscaler）机制，根据 CPU、内存以及请求量
动态调整 Pod 副本数量，同时通过 Requests 与 Limits 机制避免单个服务过度占用资源；
网络层采用双专线主备网络，结合 SLB 负载均衡实现流量自动分发，并通过 Ingress 网关
统一管理外部流量入口；数据层采用 OceanBase 分布式数据库，结合主从复制与异地灾备机制，
对热点数据通过 Redis 集群进行缓存加速，降低数据库访问压力。
在流量削峰方面，我们采用 Redis 与 RocketMQ 构建异步处理机制，请求首先写入消息队列，
再由后端服务异步处理，避免数据库被瞬时高并发直接冲击。

通过上述措施，系统在"双十一"等高峰活动期间仍能保持稳定运行，系统资源利用率提升约40%，
整体吞吐能力提升约3倍。
```

### 模块 D · 可观测性（日志 + 指标 + 链路）

**适用**：可观测性、运维架构、系统可靠性、故障定位

```
在传统运维模式下，系统故障往往需要人工登录服务器查看日志，排查效率较低，
且难以快速定位分布式系统中的性能瓶颈。因此，我们建立了统一的可观测性平台，
从日志、指标与链路三个维度对系统运行状态进行全面监控。
日志方面，基于 ELK 技术栈实现应用日志统一采集、存储与检索，通过 Filebeat 收集容器日志，
Logstash 进行数据清洗后写入 Elasticsearch，并通过 Kibana 实现日志可视化分析；
指标方面，基于 Prometheus 采集系统 CPU、内存、磁盘、网络以及应用接口响应时间等关键指标，
并通过 Grafana 构建统一监控大屏，同时配置告警规则，系统异常时自动通过企业微信发送告警；
链路方面，采用 SkyWalking 对分布式调用链路进行跟踪，能够快速定位慢接口与异常服务。
例如，在一次营销活动期间，系统响应时间明显升高。通过 SkyWalking 链路分析，
我们快速定位到订单服务数据库慢查询问题，并通过索引优化将接口响应时间由3秒降低至500毫秒。

通过可观测性体系建设，系统故障平均定位时间由原来的2小时降低至20分钟。
```

### 模块 E · 容灾与高可用

**适用**：系统可靠性、容灾设计、业务连续性、质量属性

```
为了保障系统持续稳定运行，我们从基础设施、网络以及数据层面构建了多层高可用体系。
基础设施层面采用 Kubernetes 多节点集群架构，实现服务高可用部署，当某个节点发生故障时，
Kubernetes 会自动将服务迁移至其他节点运行；网络层面采用双专线主备机制，
结合 SLB 负载均衡实现流量自动切换；数据层面采用 OceanBase 分布式数据库，
并通过主从复制与异地灾备机制保障数据可靠性。此外，我们还建立了定期容灾演练机制，
每季度开展故障恢复演练，验证系统灾备能力。
例如，在一次机房网络异常期间，系统自动切换至备用节点运行，业务仅出现数分钟波动，
未对用户造成明显影响。

通过多层容灾体系建设，系统整体可用性达到99.95%以上。
```

### 模块 F · 安全与权限（可作安全类论题主体，也可作保障段）

**适用**：系统安全性设计、数据安全、合规、权限体系

```
本项目涉及千万级会员数据与交易信息，安全要求较高。我们从权限控制、数据安全与稳定性
三个方面进行了设计。权限控制方面，采用 OAuth2 与 RBAC 权限模型，实现用户、角色、
数据三级隔离，不同项目人员只能访问本项目知识库；数据安全方面，对数据库密码、API 密钥等
敏感信息进行自动脱敏处理，对敏感字段进行加密存储；稳定性保障方面，
基于 Kubernetes 实现自动扩缩容，通过 Prometheus 监控关键资源利用率，
并配置降级机制，核心依赖不可用时自动切换到备用方案。
```

### 模块 G · 大模型 / RAG 知识库（AI 类论题专用）

**适用**：AI 应用架构、大模型工程化、智能研发、知识管理

```
仅依赖通用大模型无法满足企业业务需求，例如对于公司内部接口规范、业务规则，
大模型无法准确回答。因此，我们重点设计了 RAG 知识库系统。
在知识处理阶段，我们从 GitLab Wiki、Confluence 等渠道采集文档，按章节和代码块边界
进行智能分块（每块512 token，重叠64 token），经 BGE-large-zh 模型向量化为1024维向量后
存入 Milvus 向量数据库；在问答阶段，系统先对用户问题进行向量检索，检索时采用 Top-K=5、
相似度阈值0.7，召回相关内容后与大模型生成最终答案。
例如，当开发人员询问"订单退款流程"时，系统自动检索公司内部退款规范，生成符合业务规则的回答。

通过RAG机制，AI回答准确率从42%提升至86%。
```

AI能力层主要包括代码生成、单元测试生成、代码审查、SQL优化建议、技术问答等模块；

审查完成后在MR中直接评论问题位置及修复建议。

## 七、句库（过渡与衔接）

**引出痛点**
- 在传统模式下，……往往需要人工完成……，不仅效率低，而且容易……。

- 为解决上述问题，我们基于……理念，构建了……。

- 实践表明，……有效提升了……。
